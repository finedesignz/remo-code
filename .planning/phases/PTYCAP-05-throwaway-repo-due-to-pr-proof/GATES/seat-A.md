## F1 - VERDICT: ACCEPT-WITH-AMENDMENT (option B stays; two defects in the stated mechanism)

Evidence:
- GitHub App client EXISTS: `hub/src/auth/github-app.ts` (`getInstallationToken` :56, `githubApiGet` :79, `githubApiRequest` :112, `listInstallationRepos` :152). Installation->user mapping exists: `github_installations(user_id, ...)` schema.sql:91-99. So transport is buildable now. FORKS' `:79` cite is correct.
- Permissions are NOT sufficient as documented: `docs/HANDOFF.md:45-48` provisions the App with Contents R/W, Metadata R, Pull requests R ONLY. No Administration, no Checks. Nothing in hub/src or docs shows this was ever widened. Actual prod App permissions are UNVERIFIABLE from the repo (no prod access). `GET /repos/{o}/{r}/rules/branches/{branch}` (effective rules) needs only Metadata read; full ruleset detail incl. `bypass_actors` (needed to assert "no bypass") likely needs Administration read - UNVERIFIED. `pr_open_no_ci`/check-run reads need Checks:read, also absent from HANDOFF.
- Buildable now? YES as fail-closed code (assertion + `proof_protection_unverifiable` on 403/404/missing field), testable with a mocked `githubApiGet`. Real arm is gated on the owner adding Administration:read + Checks:read to the App and accepting the new permission prompt on the installation. That is a runbook prerequisite (a genuine credential/permission only the owner can grant), not a fallback. State it as the BLOCKER for Phase 6 live arm, not for Phase 5 code.

Refutations of the stated mechanism (amendments, binding):
1. "PR + required check" does NOT prevent a merge. Once CI is green the agent runs `gh pr merge` with the owner's credentials and the ruleset is satisfied. Prevention requires a requirement the agent cannot satisfy: ruleset MUST require >=1 approving review (GitHub forbids self-approval by the PR author; the agent's PR is authored by the owner identity) with `dismiss_stale_reviews`, and no bypass actors. Assertion shape: effective rules for the default branch include `pull_request` with `required_approving_review_count >= 1` AND `required_status_checks` AND `non_fast_forward` AND `deletion`; `bypass_actors` empty. Preferably the proof agent runs under a separate machine/bot identity with write-but-not-admin on the throwaway repo.
2. The agent holds owner gh credentials: if those are repo-admin it can edit/delete the ruleset itself, then merge. The per-tick re-assertion (proofGuard) is therefore the only thing that notices, and it is detective for that window. Amend: (a) require non-admin write identity for the agent on the throwaway repo (runbook step, asserted via `GET /repos/{o}/{r}` `permissions` on the token if readable, else documented), (b) proofGuard asserts ruleset id + `updated_at` unchanged from arm-time snapshot frozen in `orchestrator_proof_runs`, (c) verifier compares default-branch HEAD to `base_sha` AND checks no PR from the proof branch is `merged`. On any guard failure: terminal `failed`, disable task, notify.
3. Do not claim "never" in SC-1 text; claim "GitHub-enforced preventive control asserted every tick + detective backstop".
