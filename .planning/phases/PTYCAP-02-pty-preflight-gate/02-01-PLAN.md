# 02-01-PLAN — PTY pre-flight gate

## Goal (verbatim from ROADMAP.md)

"No programmatic turn reaches the PTY without passing the full gate chain."

## Success criteria (verbatim)

1. A programmatic write to the PTY passes
   `[thresholdGate, dailyTokenCapGate, dailyCostCapGate, sessionInjectRateGate]`
   or it does not happen.
2. `token-cap-coverage.test.ts` is extended to cover the PTY path.
3. Human turns are unaffected — a human at a keyboard is never gated by an
   inject-rate ceiling.

## First: verify the premise against real code

Before writing anything, audit every existing write route into a PTY session:

- `hub/src/ws/client.ts` `term.input`/`term.attach_file` relay (the web xterm
  panel / `TerminalSurface`).
- `hub/src/telegram/transcript/pty-inject.ts` `injectPtyKeystroke`, called from
  `hub/src/api/telegram-webhook.ts`'s permission/question-response callback.
- `hub/src/telegram/dispatch.ts` `dispatchToSession` (Telegram plain-text →
  `dispatch()`), which can target a pty-interactive session.
- `hub/src/ask/dispatch.ts`, `hub/src/work/dispatch.ts` — both explicitly keep
  `humanOnlyPtyGate` in their gate list and resolve the ANSWERING session to a
  stream-json repo session, never the human's PTY.

Finding: `humanOnlyPtyGate` / `humanOnlyRejectsActor` already reject every
automation actor before a write reaches a pty-interactive session — as of
Phase 1, no automation write to a PTY is possible AT ALL. The ONE gap is that
the human write path itself (`ws/client.ts`'s `term.input`) has NEVER been
checked against `dailyCostCapGate`/`dailyTokenCapGate`/`thresholdGate` — only
a license check + the human-only guard + the turn-lock sit in front of it.
`docs/usage-cost.md`'s own Phase 1 section says this explicitly: "gating the
interactive PTY path against the daily cost/token caps is milestone PTYCAP's
Phase 2, not this phase." Telegram's plain-text dispatch already goes through
the full `dispatch()` gate chain, so it is unaffected.

This reframes the phase from "stop an automation write that doesn't exist yet"
to two concrete, testable deliverables:

1. A reusable, single-source-of-truth gate chain (SC-1) that Phase 3 can call
   into the moment it admits a governed automation actor, proven correct NOW
   by unit test rather than invented under time pressure alongside relaxing
   the human-only invariant (the ROADMAP explicitly forbids parallelizing
   Phase 3 ahead of Phase 2).
2. Actually closing the real, present-day gap: gate the human PTY write path
   against the SAME spend ceilings every other inbound path already respects
   — minus the inject-rate ceiling, which exists to bound a machine that could
   loop faster than a human can type (SC-3).

## Design

`hub/src/dispatch/pty-preflight.ts`:

- `PTY_AUTOMATION_TURN_GATES = [thresholdGate, dailyTokenCapGate, dailyCostCapGate, sessionInjectRateGate]`
  — SC-1's exact order.
- `PTY_HUMAN_TURN_GATES = PTY_AUTOMATION_TURN_GATES.slice(0, -1)` — a strict
  prefix, never a hand-duplicated array, so the two chains cannot drift apart.
- `ptyPreflightDispatchConfig = { gates: [thresholdGate, dailyTokenCapGate, dailyCostCapGate, sessionInjectRateGate] }`
  — the SAME chain written with the gate identifiers INLINE (not just a
  re-exported reference) so `token-cap-coverage.test.ts`'s text-based
  `gates: [ ... ]` scan discovers this file automatically, exactly like every
  other dispatcher's `PipelineDeps`.
- `checkPtyTurnPreflight({ userId, sessionId, actor })` — runs the human chain
  for `actor === 'human'`, the automation chain otherwise; first-block-wins.

Call site: `hub/src/ws/client.ts`'s write-turn branch, immediately after the
existing human-only guard, calls `checkPtyTurnPreflight({ actor: 'human', ... })`
— but ONLY when `turn-lock.holder(sessionId) === null`, i.e. this write would
START a fresh turn. A turn already in flight already passed the check once
and is never retroactively cut off mid-keystroke; an actively-typing human
pays one DB round trip per turn, not per byte. A failing check drops the frame
(never forwarded, never acquires the turn lock) and sends a structured
`send_refused` back to the sender, mirroring the existing license-gate /
`send_message` cost-gate refusal shape.

## Explicitly out of scope for this phase

- Fixing the pre-existing, unrelated gap that `send_message` (the stream-json
  `ChatSurface` manual-chat path) is not gated by `dailyCostCapGate`/
  `dailyTokenCapGate` either — only the threshold gate runs there. This
  predates PTYCAP and is not the interactive PTY path PTYCAP is scoped to.
- Gating Telegram's permission/question-response keystroke injection — it
  answers an EXISTING pending prompt on an already in-flight (already-gated)
  turn; `turn-lock.ts`'s own documented invariant treats a response as exempt
  from turn acquisition for the same reason.
- Phase 3 (`governedAutomationPtyGate`, actually admitting a governed
  automation actor onto a PTY) — not built here; this phase only proves the
  chain that admission will have to pass.

## Test plan

- `hub/test/pty-preflight.test.ts` — chain shape/order, human-vs-automation
  split (SC-3 proven directly: human passes even when the inject-rate ceiling
  would trip), first-block-wins ordering, per-gate block/allow behavior.
- `hub/test/ws-client-pty-preflight.test.ts` — the `ws/client.ts` wiring:
  actor/session/user threading, once-per-turn (not per-keystroke) checking,
  `send_refused` + no-lock-acquired on a block, pass-through on an allow,
  pty-interactive-only scope.
- Extend `hub/test/token-cap-coverage.test.ts`'s known-dispatchers list.
- Update the two pre-existing relay tests (`term-relay-auth.test.ts`,
  `term-relay-human-guard.test.ts`) to stub `checkPtyTurnPreflight` so their
  own (unrelated) concerns don't newly require a live Postgres connection.
