## Findings

1. MED - hub/src/corch/dispatcher.ts:384-404 (and 419) - A throw before/outside the `try` leaks a live run. `governedLaunch(...)` is awaited outside the `try`; `preLaunch.checkGates` calls `runGates` with no catch, and the CORCH gates (`corchProjectBudgetGate`, `corchConcurrencyGate`, `corchQuotaGate` via `store.runContext`), `dailyCostCapGate`, `isRepoAutospawnAllowed` (`corchStore.isEnrolledEnabled`), `getTokenCapStatus` all hit the DB and can reject on a transient error. The fail-closed intent turns into an exception that escapes `launchAndDispatch` and `evaluateUser` (the evaluation loop aborts; `armNotBeforeTimer` at :500 is skipped, not in `finally`). The claimed run stays `launching` with session_id attached and attempts unchanged. The reconciler then handles it as a live session: with no fresh inventory (e.g. supervisor offline, the likely cause of the failure mix) it is marked `stalled` with an owner notification for a launch that never happened and it keeps holding the project's live-run slot and the user's cap until a fresh inventory arrives; with fresh inventory it is reclaimed as `session_absent` and burns an attempt. Same for a throw from `markRunLaunched` (:419, in the `try` but with no catch). No test covers a throwing gate/store in the launch path. Latent today (default Workspace refuses first). Fix: wrap the `governedLaunch` call and the `markRunLaunched` call in a try/catch that routes to `endRefusal(c, 'corch_error', false)` (no attempt, release reservation if reserved) or `endFailure`, and move `armNotBeforeTimer()` into a `finally` in `evaluateUser`; add a unit test with a throwing store/gate.

2. MED - hub/src/corch/reconciler.ts:34-36 with hub/src/corch/dispatcher.ts:446-460,490 - A deterministic `workspace.resolve` throw loops forever without escalation. Orphan reclaim (`claim_orphaned`) passes `consumeAttempt=false`, so the item returns to `queued` with attempts 0, `reclaimRun` immediately calls `evaluateUser`, the claim repeats, the Workspace throws again, and the cycle repeats every lease (2 min) indefinitely: never blocked, never notified, one `corch_runs` row per cycle. Latent until CORCH-09. Fix: catch `workspace.resolve` throws in `evaluateUser` and end the run via `endFailure(..., 'workspace_error')` (attempt-consuming, so it blocks after 3 with one notification) instead of relying on orphan reclaim.

3. LOW - hub/src/corch/routes.ts:93-97 (and store `updateProject`) - `PATCH /api/corch/projects/:id` passes the raw path param into a UUID column; a non-UUID id raises a Postgres error and returns 500 instead of 404. Fix: `z.string().uuid()` check on `:id`, 404 `project_not_found` on mismatch.

4. LOW - hub/src/corch/store.ts:217-229 - `enqueueWorkItem` conflict returns the existing `(user_id, source, source_ref)` row even if it belongs to a different project than the one requested; the caller gets `created:false` and an item in another project with no error. Fix: include `project_id` in the returned data check, or return 409 when `existing.project_id !== i.projectId`.

5. LOW - hub/src/corch/dispatcher.ts:470-477 - `supervisor_closed` reclaim treats a socket close as proof the session is gone, per spec. A supervisor that reconnects later (CLI kept alive; resume by project_dir) leaves the old agent running on branch `corch/<id>` while a new run is queued. Spec-sanctioned; flag for CORCH-09 (worktree lock per branch or a shutdown ack) rather than fixing here.

6. LOW - hub/test/e2e/corch-dispatcher.e2e.test.ts / tools/regression-baseline.json `_skip_note_corch_01` - the note says 25 DB-gated skips but the file has 21 `test(` entries (run with DB: 21 pass). The skip_max math (291+25) rests on the measured floor number so the gate is not weakened, but the 4-count difference is unexplained. Fix: confirm the 25 (likely describe.skip counting) and say so in the note.

7. LOW - hub/src/corch/routes.ts (all POST routes) - no cap on queued items per user/project; an `ext:corch` key can enqueue unbounded rows (rate limit on /api/ext/* only). Spend stays bounded by the gates. Fix: reject enqueue when queued count for the project exceeds a constant (e.g. 500).
