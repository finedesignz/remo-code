# Supervisor audit — 2026-05-28

Scope: `supervisor/src/**` (Bun sidecar), `supervisor/tauri/src-tauri/src/**` (Rust shell), `supervisor/test/**`. HEAD `5b30922` on `main`. Read-only.

The shell↔sidecar boundary has multiple wiring gaps that would prevent a clean MSI install from doing anything useful. The single highest-impact finding is that the Bun sidecar still tries to spawn the retired `npx -y remo-code-agent` package — the runner architecture described in the audit brief (`supervisor/src/runners/{claude-runner,session-bridge}.ts`) does NOT exist in this tree. Every `session.start` is dead on arrival.

---

## Critical (resource leak, crash that bricks the install, sandbox escape)

- **Sidecar spawns the retired `remo-code-agent` npm package** — `supervisor/src/process-manager.ts:197-203`. The hard-coded argv is `[npx.cmd, '-y', 'remo-code-agent', '--api-key', …, '--hub-url', …, '--project-dir', …]`. Phase 09 retired that package (commit `e10fa0c`, 2026-05-26). On a fresh MSI install with no global `remo-code-agent` cached, `npx -y remo-code-agent` will either resolve to a deprecated package or fail-to-resolve and the run instantly crashes → circuit breaker after 5 crashes within 10 min → `ProcessManager` removes the run, hub sees `supervisor.state stopped`, user sees "session unavailable" with no actionable error. The audit brief described a `supervisor/src/runners/{claude-runner,session-bridge,types}.ts` in-process rewrite — **those files do not exist in this tree**; only `process-manager.ts` + `watchdog.ts`. Reproducer: complete MSI first-run wizard → click "start session" in web UI → watch `%LOCALAPPDATA%\remo-code-supervisor\supervisor.log` show `[error] failed to spawn agent` or `agent exited code=1` repeatedly. Suggested fix: replace the `npx remo-code-agent` argv with a direct `claude … --input-format stream-json --output-format stream-json --verbose` spawn, wire stdin/stdout newline-delimited stream-json, and migrate the activity-event relay into the supervisor itself (the Phase 09 in-process model). Until that lands, the MSI is functionally a no-op for chat sessions.

- **Tauri commands for the Settings UI are never registered** — `supervisor/tauri/src-tauri/src/lib.rs:63`. `invoke_handler(tauri::generate_handler![])` is empty. Worse, `config_cmds.rs`, `runtime_cmds.rs`, and `legacy_cleanup.rs` are NOT declared with `mod …;` in `lib.rs` (only `first_run, mutex_probe, nssm, sidecar, tray` are). All `#[tauri::command]` functions in those three files — `get_config`, `add_root`, `remove_root`, `rescan_now`, `get_runtime_status`, `get_inventory`, `open_external_url`, `sidecar_control` — never compile in. The Settings UI's first `invoke('get_runtime_status')` call returns `"command get_runtime_status not found"`. Reproducer: `cd supervisor/tauri && cargo tauri build`; install MSI; open the Settings window from the tray. Suggested fix: add `mod config_cmds;`, `mod runtime_cmds;`, `mod legacy_cleanup;` to `lib.rs:5-9` and extend the `generate_handler![]` macro to enumerate every command. Add a unit test that asserts `tauri::generate_context!()` resolves all `invoke` calls referenced by `tauri/ui/src/lib/api.ts` (or whatever the UI uses).

- **Bun is spawned by bare-name PATH lookup; the MSI does not bundle Bun** — `supervisor/tauri/src-tauri/src/sidecar.rs:190-205`. `Command::new("bun")` relies on `bun.exe` being on the system PATH of the desktop user. The MSI bundle config (`tauri.conf.json:31-37`) declares no `externalBin` or `resources` for the supervisor src tree or a `bun.exe` shim. End-result on a clean Windows install: `spawn failed: program not found` → status flips to `Crashed` → exponential backoff up to 5 attempts → `[sidecar] giving up after max attempts` → tray shows the supervisor as crashed forever with no user-actionable error. Reproducer: install MSI on a VM with no Bun. Suggested fix: either (a) bundle `bun.exe` as `externalBin` and call it by absolute path resolved at runtime via Tauri's `path::resource_dir()`, or (b) compile `supervisor/src/index.ts` into a standalone executable via `bun build --compile` (as CLAUDE.md says is the design) and ship THAT as `externalBin`. The current `resolve_supervisor_dir` walks up `CARGO_MANIFEST_DIR` — that path doesn't exist inside the MSI install dir.

- **`ExitRequested` does not wait for the child to die before the process exits** — `supervisor/tauri/src-tauri/src/lib.rs:66-70`. `sidecar::shutdown(app)` only sets `shutdown=true` and signals the stop_notify; `app.exit(0)` returns synchronously. The lifecycle thread (a `std::thread::spawn` running its own tokio runtime, `sidecar.rs:62-67`) is in the middle of `tokio::select! { child.wait() … }` and may not have observed the notify yet. `Child::kill_on_drop(true)` mitigates this on Tokio's tokio::process child — when the runtime is dropped it tries to SIGKILL — but the kill is best-effort and on Windows TerminateProcess can race with the bun.exe → claude.exe chain (orphan claude.exe lingers; orphans seen in the wild per the user's CLAUDE.md memory rule #23 incident). Reproducer: kick a long-running session → quit the tray app → `Get-Process bun,claude` shows orphans. Suggested fix: in `lib.rs`'s `RunEvent::ExitRequested` arm, switch to `api.prevent_exit()` and await the lifecycle thread's join handle (which `spawn_managed` currently discards). Add a 5s hard timeout for the join; if it expires, only then call `app.exit(0)`. Then also propagate kill-on-children: explicitly SIGINT → wait 3s → SIGKILL, including bun → claude (which is a grandchild — needs `taskkill /T` on Windows).

## High (silent failure, lifecycle gap, untested critical path)

- **`legacy_cleanup::run_once` is dead code** — `supervisor/tauri/src-tauri/src/legacy_cleanup.rs:25` is never called from `lib.rs` or anywhere else. The whole point of this file — scrubbing the legacy NSSM `RemoCodeSupervisor` service on first launch of the new MSI — never runs. The `mutex_probe::preflight` still REFUSES to spawn when the legacy service is detected (`mutex_probe.rs:22-34`), so users upgrading from v0.3.x get a blocking dialog with copy-paste PowerShell instructions instead of automatic cleanup. This is a major regression vs. the design comment in `legacy_cleanup.rs:1-14`. Suggested fix: in `lib.rs:32 setup`, call `legacy_cleanup::run_once()` BEFORE `mutex_probe::preflight`. Adds `mod legacy_cleanup;` (same gap as the critical above).

- **Watchdog (`supervisor/src/watchdog.ts`) is not wired into the Tauri lifecycle** — the file's header comment (`watchdog.ts:5-9`) says "Task Scheduler should invoke this file directly instead of `index.ts run`." But the Tauri sidecar (`sidecar.rs:191`) spawns `bun src/index.ts run` directly, bypassing the watchdog. Result: when the sidecar crashes within 60s of start, the Rust shell does its OWN exponential backoff (capped 5 attempts → quits), and the Claude-based self-heal in `watchdog.ts:101-141` never runs. The watchdog is essentially orphan code as long as the Tauri shell is the launch path. Suggested fix: either change `spawn_child` in `sidecar.rs:188-205` to spawn `watchdog.ts` instead of `index.ts run`, or delete the watchdog entirely and document that the in-shell backoff is sufficient. The two-layer restart logic right now is contradictory: Rust gives up after 5 attempts, watchdog (if reachable) tries self-heal once.

- **`runtime_cmds.rs:128` calls `sidecar::current_status()` which does not exist** — confirmed by grep: `sidecar.rs` exports `spawn_managed, start, stop, restart, shutdown` only. Even if `mod runtime_cmds;` is added (Critical #2 fix), the build will fail. Suggested fix: add a public `pub fn current_status() -> Status { STATE.lock().status }` accessor to `sidecar.rs`. This is the smallest possible patch.

- **Sandbox check is bypassed on git operations** — `supervisor/src/hub-client.ts:212-235`. `onRepoClone`, `onRepoPull`, `onBranchCheckout`, `onListBranches` accept `repo_path` / `target_path` from the hub and pass them straight to `git-ops.ts` without running `assertWithinRoots`. The sandbox-escape gate exists only on `pm.start` (`process-manager.ts:122-136`). An attacker (or buggy hub) could `repo.clone` to `C:\Windows\System32` → race a session-start to it (sandbox blocks the start, but the clone already wrote files to a privileged dir). Suggested fix: validate every `target_path` / `repo_path` against `cfg.roots` in `hub-client.ts` before forwarding to git-ops.

- **Token leaked through `pullRepo` argv** — `git-ops.ts:91-101`. The `tokenizedUrl` (a `https://<token>@github.com/...` URL) is passed as an argv element to `git fetch`. On Windows, the full command line of any process is readable by other users via `wmic process get commandline` / WMI. The argv is also visible to any process snapshot tool (Process Explorer). `cloneRepo` (line 75-89) has the same problem on the initial `git clone`, though it scrubs `.git/config` afterward. Suggested fix: pipe credentials via a credential helper or an `askpass` shim; never put the token in argv. At minimum, document the trust model loudly.

- **No tests for the Rust shell** — `supervisor/tauri/src-tauri/src/` has only inline `#[cfg(test)]` modules for `mask_api_key` and `supervisor_id` in `runtime_cmds.rs` (an orphan file, see Critical #2). No tests for: `mutex_probe::preflight`, `sidecar::lifecycle_loop`, `tray::build` menu wiring, `legacy_cleanup`, `first_run::maybe_enable_autostart`. The lifecycle loop's backoff schedule, crash window, and shutdown ordering are entirely untested. Suggested fix: integration test that spawns a dummy "crash on start" child and asserts the 5-attempt-cap + state transitions emit the expected `supervisor:status` events.

- **`no-legacy-agent-spawn.test.ts` referenced in audit brief doesn't exist** — `supervisor/test/` contains: `error-setup-apply.test.ts`, `error-setup-probe.test.ts`, `git-introspect.test.ts`, `process-manager.test.ts`, `repo-scanner.test.ts`, `sandbox.test.ts`. The "legacy agent spawn" guard test the audit brief expected is missing. Existing `process-manager.test.ts` actively asserts the `npx remo-code-agent` argv is correct (lines 153, 160, 167 check for `--dangerously-skip-permissions`), which means the test suite would BLOCK any fix that migrates off the retired package. Suggested fix: write `no-legacy-agent-spawn.test.ts` that fails if `cmd[1]` is `remo-code-agent`, and rewrite the dangerously-skip-permissions tests to match whatever the new spawn argv shape becomes.

- **First-run marker is not version-scoped** — `first_run.rs:9-12`. The marker file is `.first-run-done` with no version suffix. The brief asked specifically whether the marker is per-version; it is NOT. Once a user installs v0.3.1 and the marker is set, a future v0.5.0 with a re-introduced welcome dialog won't re-prompt. (Compare to `legacy_cleanup.rs:18` which uses `.legacy-nssm-cleanup-done-v0.4.2` — that file gets it right; first_run does not.) Suggested fix: bump to `.first-run-done-v{CARGO_PKG_VERSION}` so each major change can re-introduce the welcome.

- **MSI uninstall does not remove HKCU Run autostart key** — there is no `tauri.conf.json` `bundle.windows.wix` or NSIS section, and `tauri-plugin-autostart` writes to `HKCU\…\Run` on enable but exposes no uninstall hook in the MSI flow. After uninstall, the dead path still attempts to start on next login (silent fail because the .exe is gone). Reproducer: install → quit → uninstall → `Get-ItemProperty HKCU:\Software\Microsoft\Windows\CurrentVersion\Run`. Suggested fix: add a `wix` uninstall custom action (or Tauri 2 NSIS hook) that calls the autostart plugin's `disable` before file removal.

## Medium (observability, error-recovery, polish)

- **`ws.onerror` is silent** — `hub-client.ts:117-119`. "onclose will follow" assumes onclose ALWAYS fires after onerror. That holds for actual network errors but not for synchronous WebSocket construction failures (e.g. invalid URL scheme). Edge case is small but the assumption is undocumented. Suggested fix: log the error event details before relying on onclose to handle reconnect.

- **`bun:fileWriting` stream in `setupFileLogging` never gets closed** — `supervisor/src/index.ts:34`. `createWriteStream(logPath, { flags: 'a' })` is captured in the `tee` closure; on `SIGINT/SIGTERM` (line 117-118) `process.exit(0)` runs synchronously without flushing the stream. Up to 64KB of pending log lines can be lost on a clean shutdown. Suggested fix: register a `process.on('beforeExit')` that calls `stream.end()`.

- **`repo-scanner.ts` only goes one level deep** — `repo-scanner.ts:41-61`. Confirmed single-depth (matches the audit brief's expectation). However, `entry.startsWith('.')` (line 47) skips `.dotted` dirs but does NOT detect symlink loops — `isDir(path)` (line 49) follows symlinks via `statSync`. A configured root containing a symlink loop (`foo/foo/foo/…`) would not crash because of the single-depth limit, but `realpath`-resolution would still hang on a deeply nested loop. Not a bug today; document and bound.

- **`git-config` parser is regex-only and accepts the FIRST `url =` line under `[remote "origin"]`** — `repo-scanner.ts:21`. A `.git/config` with multiple origin URLs (rare but legal — e.g. `pushurl =` and `url =` on separate lines) returns the first match regardless of key. Not security-critical, but `read_remote` may return a `pushurl` when the user expected `url`. Use `git config --get remote.origin.url` instead for robustness (slower; trade-off documented in `repo-scanner.ts:38`).

- **`hub-client.ts` `onSessionStatus` ignores `req_id`** — `hub-client.ts:304-311`. The hub sends `req_id` but the response (`supervisor.state`) has no `req_id` field, so the hub cannot correlate replies in flight. Suggested fix: thread `req_id` through `supervisor.state` or add a separate `supervisor.state_result` message.

- **`process-manager.ts` env hygiene**: `delete env.ANTHROPIC_API_KEY` (line 211) is good, but the audit brief mentioned `CLAUDE_CODE_USE_BEDROCK` and custom env from hub payload. Neither is plumbed today. `runSpec` has no `env` field. Bedrock users cannot use this supervisor.

- **`mutex_probe.rs:51-56` probes via TCP connect** — if some unrelated service binds 9106 (e.g. a user's own app), the supervisor refuses to start with a misleading "another supervisor is running" dialog. Suggested fix: send a tiny HTTP/WS handshake and verify the server identifies as a remo-code supervisor before declaring collision.

- **`hub-client.ts:13` outbound message `supervisor.hello` is sent AFTER `auth_ok`** — but the `auth` message at line 84 uses `project_dir: '__supervisor__'`. The hub's agent protocol (`hub/src/ws/agent.ts`) expects `cli_kind` and `rootless_session_ids` (per CLAUDE.md Phase 05). This client sends neither, which matches the memory note `project_handoff_supervisor_ws_close.md`: the hub `AgentInbound.safeParse` would silently reject the hello and close the socket with no `authenticated` log on the supervisor side. That handoff appears not to have been addressed in this audit's branch.

- **Audit log: no per-process file lock** — `audit.ts:38-48` uses `appendFileSync` which on Windows is NOT atomic across multiple supervisor processes. Mutex probe prevents two supervisor processes in normal use, but the diagnostic `bun src/index.ts scan` path also calls `loadConfig()` (no audit write) — risk is low but unbounded if a user has the legacy NSSM running concurrently. Already covered by the mutex probe gate, but if that gate were bypassed (e.g. preflight crashed), audit log corruption is possible.

- **`watchdog.ts:91-99 findClaudeBinary`** lists three candidates but doesn't probe PATH. On most user installs `claude` is on PATH via `~/.npm-global/bin` or `~/.bun/bin` — neither candidate. Fallback to bare `claude` (line 98) is correct but should be the first thing tried; the candidates feel speculative.

- **`commands-scanner.ts` walks `~/.claude/skills` non-recursively, but `~/.claude/plugins/cache/<market>/<plugin>/<version>/skills` recursively** — `commands-scanner.ts:97-103` vs `121-126`. Inconsistent depth. User skills nested two-deep are missed; plugin skills are not.

- **`commands-scanner.ts:48` `walkMd` depth cap is 5** — for `~/.claude/commands/`, perfectly reasonable. But there is no entry-count cap; a maliciously crafted commands dir with 100K .md files would OOM the supervisor at boot during `scanAllCommands()`. Add a 5000-file cap.

- **`runtime_cmds.rs:222-249 open_external_url`** only validates `http(s)://`. On Windows, `cmd /C start "" "http://…"` passes the URL through `cmd.exe` parsing — a URL containing `&` or `^` could be interpreted as shell metacharacters. Use `ShellExecuteW` directly via the `windows` crate (already a dep) instead of `cmd /C start`.

- **`first_run.rs:38` blocking dialog at startup** — `blocking_show()` from `tauri-plugin-dialog` halts the main event loop. On a user with autostart enabled, this means every fresh install's first login shows a modal dialog the user has to dismiss before the tray icon appears. Consider a non-blocking notification.

- **`tray.rs:38` `tray.png` is included via `include_bytes!` from `../icons/tray.png`**, but the file at that relative path is NOT in the git status I observed. If it's missing at build time, `.expect("tray.png missing")` panics on tray init → tray never appears → user has no UI to recover. Confirm the file exists in `supervisor/tauri/src-tauri/icons/`.

- **Process manager spawnImpl test hook is `public`** — `process-manager.ts:52`. Production code shouldn't have a publicly mutable test hook. Wrap in `#if TEST` or move to a subclass. Minor.
