# Sessions audit — 2026-05-28

Scope: chat session lifecycle + message-history integrity. Out: orchestrator/*, web/src/**, supervisor/tauri/**, `sessions.is_orchestrator`.
Repo HEAD: `5b30922` on `main`.

## Critical (data loss, message reorder, duplicate persistence, cap bypass)

- **Scheduled-run finalize mis-attributes manual user replies as scheduled completions** — `hub/src/scheduler/senders/agent.ts:85-106` + `hub/src/ws/agent.ts:432-435`. `sendAgentTask` pushes to `pendingTurns[sessionId]` (FIFO) and `onAssistantMessage` unconditionally shifts the head on the *next* `assistant_message` for that session. Manual `send_message` from the user via `/ws/client` does NOT enter `pendingTurns` but Claude's reply to that manual prompt arrives as a regular `assistant_message`. Reproducer: scheduled run dispatches → user immediately types a quick question via the web UI → Claude responds to the user → `onAssistantMessage` pops the scheduled-run head and marks it `success` with the user-reply snippet; the *actual* scheduled response (which lands next) finds an empty queue and falls through. Net: scheduled `output_snippet`, `duration_ms`, and `cost_usd` are wrong, and a real scheduled completion is silently dropped. Fix: gate pendingTurns by matching the `run_id` echoed on the `assistant_message` (the dispatcher already tags the outbound `user_message` with `run_id`; have the agent runner echo it back), OR fence the session against manual sends while `pendingTurns[sid].length > 0`.

- **Hub never finalizes `session_runs` on agent socket close** — `hub/src/ws/agent.ts:688-722` (`handleAgentClose`). Only sets `sessions.status='offline'` and unregisters the channel. `session_runs.ended_at` stays NULL until the *supervisor* sends `supervisor.state` with `last_exit` (`hub/src/ws/agent.ts:584`). If a supervisor process dies without graceful shutdown (kill -9, OOM, uninstall), every running `session_runs` row stays open forever. `reserveSessionSlot` (`hub/src/sessions/budget.ts:64-69`) counts those zombies against the cap → all subsequent reservations 503 with `at_capacity`. Reproducer: `pkill -9 remo-code-supervisor` mid-run → row never closes → cap never frees. Fix: on `handleAgentClose` for `role='supervisor'`, run `UPDATE session_runs SET ended_at=now(), exit_reason='socket_close' WHERE supervisor_id=$1 AND ended_at IS NULL`. Auto-resume on reconnect already does this (line 508) but only IF the supervisor reconnects — uninstall/permanent death leaves the cap pinned.

- **`/ws/client` bypasses the license gate entirely → expired-license users can still mutate** — `hub/src/index.ts:299-353` upgrades `/ws/client` before any Hono middleware. `hub/src/ws/client.ts:240-373` `send_message` checks `checkUserThreshold` only, never `license_status`. `CLAUDE.md` (Phase 07 invariant) states user-initiated mutations MUST be blocked when `license_status='expired'`. Currently a user with expired license has full WS write access (send_message, permission_response, question_response) — only HTTP mutations are gated by `requireActiveLicense` (`hub/src/index.ts:172-179`). Fix: pull `getUserLicenseFields` into the WS `auth` handler, store on `ws.data.licenseStatus`, refuse mutating WS message types when not `active` (mirror the HTTP gate's `readOnlyOk` exemption for `subscribe`/`pong`).

- **Subscribe cap-violation handled by silent schema drop instead of `subscribe_error`** — `hub/src/ws/protocol.ts:40` enforces `session_ids: z.array(...).max(SUBSCRIBE_MAX)` at parse time. `hub/src/ws/client.ts:71` does `safeParse(...).success` → return; no error to the client. The handler-level `subscribe_error` at `client.ts:172-179` is unreachable for >12 ids because the schema rejects first. Contract drift: the protocol's documented "`{ type: 'subscribe_error', error: 'too_many_sessions', max: 12 }`" payload (`hub/src/ws/protocol.ts:206`) is only emitted on the 12 edge case which the Zod schema already rejected. Fix: relax the schema cap to a higher bound (e.g. 64) so the handler-level check runs, or send `subscribe_error` from the safeParse-fail path when discriminator is `subscribe`.

## High (silent drop, race, contract drift)

- **Phase 08 test suite imports symbols that don't exist** — `hub/test/session-keying-dal.test.ts`, `hub/test/phase-08.e2e.test.ts`, `hub/test/sessions-pending.test.ts`, `hub/test/sessions-launch.test.ts` (mock declarations) reference `dal.findOrCreateAgentSessionV2`, `getPendingPrompts`, `dismissLocalSession`, `sessions.repo_key`/`github_owner`/`github_repo`, `pending_local_repos`/`dismissed_local_sessions` tables, `resolveLocalPathForRepoKey`, `getUserInventory`, `getKnownLocalPathsForRepoKey`, `enqueueCreateGithubRepoJob`. None exist in `hub/src/db/dal.ts`, `hub/src/db/schema.sql`, `hub/src/ws/supervisor-registry.ts`, or `hub/src/lib/`. Tests are gated on `REMO_E2E_DB_URL` (DAL ones) or use `mock.module` to fake the surface, so they appear to pass — but they're testing scaffolding from a Phase 08 plan that never landed on `main`. False sense of coverage. Fix: either land the Phase 08 DAL+schema changes or delete the orphan tests.

- **`streamingBySession` map is never cleared on agent disconnect** — `hub/src/ws/agent.ts:30` (definition) + `handleAgentClose` (lines 688-722). When an agent socket dies mid-stream, the streaming placeholder row stays at `status='streaming'` in Postgres AND the in-memory entry survives. On agent reconnect (same `session_id` because resume keys on `project_dir`), the very next `text_delta` reuses the stale `placeholder.id` (`agent.ts:338-343`) and appends Claude's new turn to the dead placeholder row. The on-boot sweep `markStreamingMessagesAsInterrupted` (dal.ts:228) only runs on hub restart, not on agent reconnect. Net: cross-turn content corruption. Fix: in `handleAgentClose` for `role='agent'`, `streamingBySession.delete(ws.data.sessionId)`. Also in `registerChannel` when replacing an existing channel (`registry.ts:25-28`), since channel replacement also indicates a stale state.

- **No client-initiated cancel** — `hub/src/ws/protocol.ts:66-73` `ClientInbound` has no `cancel` variant. `hub/src/ws/client.ts` has no handler for it. The `HubToAgent` cancel type at line 200 is wired only by the scheduler dispatcher (`scheduler/dispatcher.ts:481`). The audit brief, `CLAUDE.md`, and `docs/scheduled-tasks.md` all describe user-initiated cancel as a feature — none of that flow exists in code. Web UI users have no way to abort a runaway Claude turn. Fix: add `ClientCancel = z.object({ type: z.literal('cancel'), session_id: z.string(), csrf_token: ... })` to `protocol.ts`, handle in `client.ts` (ownership check + forward `{type:'cancel'}` to the channel), and have the agent runner translate to SIGINT/stdin-close. Also document the `session_runs.exit_code` sentinel for cancel (currently no convention).

- **`findOrCreateAgentSession` is NOT atomic against concurrent connects with the same `project_dir`** — `hub/src/db/dal.ts:119-139`. Path: `findSessionByProjectDir` SELECT → if not found, INSERT. Two agents authenticating at once for the same `(user_id, project_dir)` both miss the existing row, both insert, both succeed. `idx_sessions_user_project` is a *non-unique* index (`schema.sql:27`). Net: duplicate session rows with the same `project_dir`; subsequent connects randomly pick one via `ORDER BY last_activity DESC NULLS LAST LIMIT 1`. The rootless variant `findOrCreateRootlessSession` (dal.ts:80-115) handles this correctly with `ON CONFLICT DO NOTHING` + re-SELECT against the partial unique index. Project sessions have no equivalent guard. Fix: either add a partial unique index `(user_id, project_dir) WHERE deleted_at IS NULL AND is_rootless = false`, or mirror the rootless dance in `findOrCreateAgentSession`.

- **Messages ordered solely by `created_at` (microsecond precision, no tiebreaker)** — `hub/src/db/dal.ts:182` `ORDER BY m.created_at ASC`, `hub/src/db/chat-tabs-dal.ts:260,271`. `id` is `gen_random_uuid()` — non-monotonic. Two near-simultaneous inserts (e.g. user `send_message` racing the `insertAssistantPlaceholder` triggered by Claude's first text_delta) can share a `now()` microsecond and return in undefined order. The grid view's batch endpoint inherits this. Fix: add a `bigserial` `seq` column (or `id` ULID), tiebreaker `ORDER BY created_at ASC, seq ASC`. Cheap, monotonic, breaks no API.

- **No empty/whitespace rejection on `send_message`** — `hub/src/ws/protocol.ts:17` `z.string().min(1).max(1_000_000)`. A single space passes. `hub/src/ws/client.ts:279` persists it and forwards to Claude. Brief explicitly called this out; gap stands. Fix: `.trim().min(1)` or post-parse check, return a structured `send_refused: 'empty_content'`.

- **No double-submit dedupe on `send_message`** — `client.ts:240` reads `msg.id` (client-supplied UUID, schema-validated) but never checks DB or memory for prior persistence. A flaky network where the client retries with the same `id` produces two `messages` rows (different `messages.id` since DAL auto-generates). The `send_ack` ACK pattern (line 285-294) helps but the client decides retry policy. Fix: track `(session_id, client_id)` for ~5 min in-memory (or unique index) and short-circuit duplicates with a replayed `send_ack`.

- **`sessions.cli_kind` is NOT enforced as immutable post-creation** — `dal.ts:14` `updateSessionAgentInfo` does only `agent_info` and `dal.ts:152` `updateSessionStatus` only `status`. But there is no DB constraint preventing a future patch from updating `cli_kind` after first insert. `findOrCreateAgentSession` at line 128 explicitly does NOT change `cli_kind` on the reuse path (good), but a misbehaving agent or new code path could. Fix: explicit `ALTER TABLE sessions ADD CONSTRAINT sessions_cli_kind_immutable CHECK ((cli_kind IS NOT NULL))` plus a row-level trigger (`OLD.cli_kind = NEW.cli_kind`) — Postgres has no native column-immutable; trigger is the standard pattern.

## Medium (observability, polish, error-path)

- **`session_runs.restart_count` is set on initial insert but never incremented** — `supervisor-dal.ts:188` writes `restart_count` from the input arg; agent.ts:518 auto-resume insert does NOT pass `restart_count`, so it defaults to 0 every reboot. The intent (per column name + comment) is to count restarts of one logical session over time. Fix: when `restart_of` is set, copy `parent.restart_count + 1`.

- **`pendingTurns` 30-min `TURN_TIMEOUT_MS` timer outlives session lifecycle** — `senders/agent.ts:108-117` `setInterval` runs forever, scans every session's pending queue. If the session is soft-deleted (`sessions.deleted_at`), the queue isn't purged; the timer harmlessly drains it eventually, but `finalizeRun` still writes to a `session_runs` row that's been orphaned. Low blast radius. Fix: call `abandon(sessionId)` from `deleteSession` and `handleAgentClose`.

- **`broadcastToSubscribers` swallows all socket errors** — `ws/registry.ts:74` `try { client.ws.send(json) } catch {}`. A backpressured or dead-but-not-cleaned-up client never gets the event — and the next event drops too. The audit brief flagged this. There's no detection of "slow client" — only the per-IP connection limit (`MAX_WS_CONNECTIONS_PER_IP=20`). Fix: track `send` return (Bun returns -1 on closed) and unregister the client when consecutive sends fail.

- **`subscribeClient` replaces the Set under the hood, BUT `broadcastToSubscribers` iterates `clients` (Set) directly** — `ws/registry.ts:65-67,70-77`. If a Set mutation happens mid-iteration (a register/unregister during a broadcast loop), V8/Bun semantics permit skipped entries. The broadcast loop is synchronous and `clients` mutations only happen on `register`/`unregister` (called from WS handlers serialized by the event loop). So in practice it's fine — but the contract is fragile. Fix: snapshot to an array first or use a `for...of` with `[...clients]` spread.

- **Soft-delete sessions still appear in `chat_tab_sessions` cascade** — `schema.sql:285-291`. `chat_tab_sessions.session_id REFERENCES sessions(id) ON DELETE CASCADE` — but `deleteSession` is soft (`UPDATE ... SET deleted_at`), not a row delete. Soft-deleted sessions remain in the tab; only the JOIN filter `s.deleted_at IS NULL` in `chat-tabs-dal.ts:58,158` hides them. Net: tab membership row leaks until the row is hard-deleted. Fix: when soft-deleting, also `DELETE FROM chat_tab_sessions WHERE session_id = $1`. Same applies to `scheduled_tasks.session_id` (FK SET NULL) — soft-delete leaves the FK live.

- **`recentlyDisconnectedForProjectDir` uses 30s window, NOT user-configurable** — `dal.ts:43-57` + `agent.ts:201`. A user who disconnects and immediately changes their mind has to wait 30s before the agent can reconnect cleanly. Not a bug, but a UX cliff. Document or expose.

- **`agent_info.hostname` precedence is unclear** — `agent.ts:230` `hostname: (msg as any).agent_info.hostname || msg.hostname`. Agent can lie about its hostname via either field; rootless session creation uses `msg.hostname || msg.agent_info?.hostname` (line 246), opposite precedence. Net: same agent, two values, depending on which write path. Fix: pick one source of truth — preferably the protocol-validated top-level `msg.hostname`.

- **No test coverage for the streaming-message lifecycle** — `markStreamingMessagesAsInterrupted` (dal.ts:228), `insertAssistantPlaceholder` (dal.ts:196), `appendToMessage` (dal.ts:206), `finalizeMessage` (dal.ts:216). No test verifies: (a) what happens when `assistant_message` lands without a prior `text_delta` (line 421 fallback path), (b) what happens when `appendToMessage` races `finalizeMessage` (the `WHERE status = 'streaming'` guard prevents post-finalize appends — good — but no test exercises it), (c) the boot sweep correctly flags orphans. Gap given how central this is to chat integrity.

- **`reserveSessionSlot` is atomic per-supervisor, but the *user-level* daily cost cap is not** — `budget.ts:37-76` locks the supervisor row. The dispatcher's daily-cap check (`scheduler/dispatcher.ts` `enforceCostCap`) reads + writes without a lock. Two simultaneous scheduled runs can both pass the cap check, both run, both bill. Out of scope but visible from the routing → budget chain. Note for the orchestrator agent.

## Notes

- `sessions.is_orchestrator` column referenced by the brief is NOT present in `hub/src/db/schema.sql` on this HEAD. The orchestrator agent's column has not landed. No regression to flag — the column simply doesn't exist yet.
- The agent send path's `forwardPayload.run_id` is set ONLY by the scheduler sender (`senders/agent.ts:78`), never by user manual sends. Adding `run_id` symmetry on the manual path (echoed back by the runner on `assistant_message`) would be the cleanest fix to the Critical #1 mis-attribution bug.
- The catchup-on-reconnect contract (browser tab reconnects to `/ws/client` mid-stream): on auth, server sends `session_list` (line 119) and the user's current `subscription_usage` (line 124), but does NOT replay any in-flight `text_delta` events — the streaming placeholder row is fetched lazily via the messages REST endpoint when the user re-opens the session. Acceptable, but undocumented. Worth a one-paragraph note in `CLAUDE.md` so future agents don't try to "fix" this by adding replay.
- `hub/test/sessions-launch.test.ts` is essentially testing imaginary code via `mock.module`. Same for `phase-08.e2e.test.ts` (which would fail at `dal.findOrCreateAgentSessionV2` import if `REMO_E2E_DB_URL` were set). High priority to triage these — they're hiding behind skip-gates.
